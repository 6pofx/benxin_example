# 示例 14 · 代码编排（flow）—— 差旅报销审批

> 把一张**真实业务流程图**用 Java 写出来，跑在本机 LM Studio 的模型上。
> 规则交给代码（金额、校验位、分级、科目），判断交给模型（类别、风险、审批结论）——
> 并且用**输出契约**保证模型只吐枚举值，让分支真的可靠。

```bash
cd benxin_exp && mvn -o install -DskipTests
cd exp-14-expense-approval-flow && mvn -o spring-boot:run   # 需要本机 LM Studio
```

---

## 一、场景：一家公司的差旅报销

员工在 OA 里提交一段报销说明（自然语言），财务共享中心要完成：

1. **收单解析**：抽出金额、发票号、部门、出差日期；验发票校验位；对照制度上限；
2. **判断**：这笔费用属于哪一类、风险有多高；
3. **分级**：按"风险 × 金额"决定走自动通过 / 部门经理 / 财务总监；
4. **审批**：审批人给结论（通过 / 驳回 / 需补充材料）；
5. **补件**：材料不全就退回补交，补完重新进流程；
6. **记账**：通过后生成会计凭证。

这是很典型的一类流程：**规则很硬，判断很软**。制度写死了"超过 1 万要总监批"，
但"这笔 12800 元的机票酒店有没有风险"只能由人（或模型）看材料判断。

## 二、这张图长什么样

用 `JavaFlow` 写在 [`flow/ExpenseApprovalFlow.java`](src/main/java/com/benxin/exp/expense/flow/ExpenseApprovalFlow.java)，运行时会打印导出的 Mermaid：

```
A 员工提交报销说明
B 收单解析（代码：金额 / 发票号 / 校验位 / 上限）
  ├─ REJECT    ─→ C1 退回通知 ─→ C2 结束（无法受理）
  ├─ NEED_INFO ─→ N 补件 ─┬─ 还能补 ─────→ B（回边，重新解析）
  │                       └─ 补件超限 ────→ O 结束（超时关闭）
  └─ OK ─→ D 类别识别（模型）
             → E 风险评估（模型）
             → F 分级（代码：风险 × 金额）
                  ├─ AUTO     → G1 系统自动通过 ──────┐
                  ├─ MANAGER  → H 部门经理审批 ──────┤
                  └─ DIRECTOR → I 财务总监审批 ──────┤
                                  ├─ 通过 ────────────┴→ L 记账凭证 → L1 结束（通过）
                                  ├─ 驳回 ──────────────→ M 驳回通知 → M1 结束（驳回）
                                  └─ 需补充材料 ────────→ N 补件（回边）
```

**17 个节点 / 23 条边 / 4 个出口 / 2 条回边**，代码里分段成五个方法
（`intake` / `judge` / `approval` / `settle` / `supplement`），主方法只有六行。

## 三、代码怎么对应到图

| 节点 | 类型 | 谁来做 | 做什么 |
|---|---|---|---|
| `A` | start | — | 把员工原文放进黑板 |
| `B` | **code** | `IntakeNode` | 正则抽金额与发票号、验校验位、对照上限 → `claimStatus` |
| `D` | **agent** | 模型（输出契约） | 类别四选一：交通 / 住宿 / 餐饮 / 其他 |
| `E` | **agent** | 模型（输出契约） | 风险三选一：低 / 中 / 高 |
| `F` | **code** | `GradeNode` | 风险 × 金额 → `AUTO / MANAGER / DIRECTOR / ESCALATE` |
| `G1` | **code** | `AutoApproveNode` | 系统自动放行（低风险小额），不调模型 |
| `H` / `I` | **agent** | 模型（输出契约） | 经理 / 总监审批：通过 / 驳回 / 需补充材料 |
| `L` | **code** | `VoucherNode` | 科目映射 + 凭证号流水 |
| `M` | **code** | `RejectNode` | 驳回 / 退回通知 |
| `N` | **code** | `SupplementNode` | 生成补件清单，写回 `pendingSupplement` |

**四个模型节点都声明了 `choice`**：

```java
.agent("H", MANAGER_SYSTEM,
       "请以部门经理身份审批…（通过 / 驳回 / 需补充材料）",
       "通过", "驳回", "需补充材料")          // ← 输出契约
```

运行时做三步：**归一化**（去围栏 / 加粗 / 引号 / 尾标点 / "结论："前缀）→
**判定**（精确匹配或唯一子串；"不通过"绝不算"通过"）→ **纠正重试**（最多 2 次）。
判不出来就让节点失败，而不是把模糊答案当枚举值塞给下游 —— 于是
`routeFrom(...).caseOf("通过", ...)` 的精确匹配才有保障。

## 四、真跑一遍（本机 Qwen3-VL-8B，五个场景）

```
场景一  小额 + 资料齐全            A B D E F G1 L L1        AUTO     380 元   交通  低   2 次模型
场景二  中等金额                  A B D E F H L L1         MANAGER  3600 元  住宿  低   3 次模型
场景三  大额                      A B D E F I L L1         DIRECTOR 12800 元 交通  中   3 次模型
场景四  缺发票号                  A B N N1 B D E F H L L1  MANAGER  520 元   餐饮  中   3 次模型
场景五  连金额都没有               A B C1 C2                —        0 元     —     —   0 次模型
```

三个值得看的地方：

- **场景四的 `B` 出现了两次**：补件不另写一条路，而是把补的材料拼进解析输入、
  绕回收单节点重跑同一段逻辑。回边在 `visited` 里看得见。
- **场景五一次模型都没调**：`usage` 是 `0/0`。资料不足以进入审批时，
  流程在 `B` 就分流到退回，后面的模型节点根本到不了 —— 这也是"模型只在被点名处出现"的直接证据。
- **场景三模型判"中"风险、金额 12800**：分级规则（> 1 万走总监）生效，
  轨迹落在 `I`。风险是模型给的，审批线是代码算的，两者在 `F` 汇合。

一次完整演示（5 个场景、11 次模型往返）在本机实测约 **7 秒**、**1629 tokens**，全部是本地推理。

## 五、为什么这么分工

| | 交给模型 | 交给代码 |
|---|---|---|
| 例子 | 类别、风险、审批结论 | 金额求和、发票校验位、分级阈值、科目、凭证号 |
| 为什么 | 需要理解自然语言里的意图 | 有唯一正确答案，错了就是财务事故 |
| 失败时 | 输出契约兜底：重试 → 失败 | 单元测试兜底：改一行就红 |
| 可复现 | 不完全（同输入可能不同判断） | 完全 |

这也是代码编排相对 YAML 的实际收益：**节点是对象，能注入依赖**。
`VoucherNode` 拿到的是 `AccountingService`，`GradeNode` 拿到的是 `ExpensePolicy` ——
测试里换一份构造参数就能覆盖所有金额边界，不需要起 Spring，更不需要模型。

## 六、有三个"容易猜错"的口径

1. **代码节点返回的变量名不能和节点 id 一样。** 节点 id 那个键永远代表它自己的输出，
   同名变量会被覆盖（这条与 YAML 模式一致）。
2. **不要用参数去传"可能不存在的变量"。** 驳回通知既可能来自经理（`${H}`）也可能来自总监（`${I}`），
   硬写 `${H}` 时走总监路径会把它渲染成字面量 `${H}`（模板的规则是"解析不到就保留原文"）。
   正确做法是从黑板读（`RejectNode` 就是这么写的），或者让节点自己推导。
3. **`Mermaid.toMermaid` 会把过长的描述截断**（超长加 `…`）。图是给人扫一眼的，
   要看全文去读 `describe(...)` 的原文。

## 七、运行与参数

```bash
# 前置：LM Studio 里加载 qwen/qwen3-vl-8b 并启动本地服务器（默认 1234）
cd exp-14-expense-approval-flow

mvn -o spring-boot:run          # 五个场景跑一遍（约 7 秒）
mvn -o test                     # 28 个用例；LM Studio 不可用时真实调用那 3 个自动 skip
```

| 开关 | 默认 | 作用 |
|---|---|---|
| `exp.demo.print-graph` | `true` | 是否在演示里打印 Mermaid 图 |
| `exp.expense.auto-approve-limit` | `2000` | 低风险且不超过此金额 → 系统自动通过 |
| `exp.expense.manager-limit` | `10000` | 不超过 → 部门经理；超过 → 财务总监 |
| `exp.expense.single-claim-limit` | `20000` | 超过 → 需分管副总签批（ESCALATE） |
| `exp.expense.max-supplement-rounds` | `2` | 补件最多几轮，超过按超时关闭 |
| 环境变量 `LOCAL_MODEL_ID` | `qwen/qwen3-vl-8b` | 换成本机已加载的其它模型 |

## 八、测试：28 个用例，只有 3 个碰模型

| 测试类 | 数量 | 要模型 | 钉住什么 |
|---|---|---|---|
| `ExpenseRulesTest` | 16 | 否 | 发票校验位、金额解析（多笔 / 千分位 / 缺件 / 超限）、分级边界 |
| `ApprovalGraphTest` | 9 | 否 | 四条出口的轨迹、补件回边（`B` 两次）、无法受理零模型调用、17/23/4 结构、Mermaid 导出、不可序列化 |
| `ExpenseApprovalRealTest` | 3 | **是** | 真实模型端到端：轨迹与审批线自洽、补件回边、零 token 路径 |

两点说明：

- **`ApprovalGraphTest` 用脚本模型**，因为"哪条结论走哪条边"必须是确定性的；
  真模型的判断不该被钉死在测试里。它与演示是两回事：**演示只用真模型**。
- **真实模型测试的断言分两层**：确定性事实（金额、轨迹、账务字段）精确断言；
  模型判断（类别 / 风险 / 结论）只断言"内部自洽"（轨迹必须与 `approvalPath` 对得上）。
  把小模型的判断钉死，测试就变成了"今天模型心情如何"的记录。

## 九、和工作流另外两种写法的关系

| | exp-05 `workflow` | exp-13 `java` 节点 | **exp-14 `flow`（本模块）** |
|---|---|---|---|
| 图写在哪 | YAML / JSON 配置 | YAML 里挂 Java 处理器 | **Java 代码** |
| 节点行为 | `handler:` 名字 | 注册表里的对象 | **直接绑定的对象** |
| 边条件 | `when:` 表达式 | 同左 | **`Predicate<FlowView>`** |
| 可序列化 | 是 | 是 | **否**（`WorkflowIo` 明确拒绝） |
| 适合 | 运维可改的流程 | 图在配置、个别步骤要写代码 | 规则复杂、要类型安全与依赖注入 |

三者**共用同一个引擎**：边序优先级、`maxVisitsPerNode` 护栏、节点级 `retry` /
`continueOnError`、步数预算、事件与变量回写，语义完全一致 —— 换写法不用重学一套语义。
